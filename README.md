# kintoreapp

1人用の筋トレ記録アプリ。簡単な記録と朝倉栞との日常を通じて、また開きたくなる体験を作る。Android縦画面、データ保全、原則無料、休んだ日を責めない設計を重視する。

## 現行の個人用認証

Cloudflare Zero Trust / Accessは使用しない。Runtime Secret `APP_PASSWORD`に設定した1つのパスワードでログインする。方式を独断で変更せず、Secretをコード・ログ・会話へ出さない。ユーザーにSecretの送信を求めない。

| 項目 | 現行実装（正確な処理は`src/index.js`） |
|---|---|
| Secret長 | 最低4文字、最大200。下限はコードポイント数、上限はJavaScriptの`length`で判定 |
| Cookie | `kintore_session`、署名付き、14日間 |
| 属性 | `HttpOnly; Secure; SameSite=Strict; Path=/api` |
| 署名鍵 | `APP_PASSWORD`から導出。パスワード変更は既存Cookieにも影響 |
| 書き込み保護 | loginとworkoutsは同一Origin＋JSON。logoutは同一Origin |
| 制約 | 専用レート制限は未実装。最短4文字は推測に弱いため、長いランダムなパスワードを推奨 |

ログイン前は簡素なパスワード入力のみ。アプリ名・筋トレ説明・キャラクター演出を追加しない。UIの匿名性と公開リポジトリ・静的ファイルの公開範囲は別である。個人記録APIには認証が必要。

初回のSecret設定はCloudflareの対象Workerの設定から、Variables and SecretsにType **Secret**、Name **APP_PASSWORD**で登録する。通常の公開変数へ入れない。

## 永続保存とD1

- コード・正式仕様・採用済み素材・固定セリフ：GitHub。
- 個人の筋トレ記録、今後の設定・予定・会話履歴：原則Cloudflare D1。
- `localStorage`、`IndexedDB`等へ個人データを永続保存しない。認証Cookieと操作中のメモリ状態は許容。
- 固定コンテンツやブラウザの通常の静的キャッシュと、個人データの保存は区別する。個人の会話・記録を公開GitHubへ置かない。

[初期SQL](migrations/0001_initial.sql)の`workout_sessions`と`workout_sets`を筋トレ実績・種目別セット保存に使用する。追加SQL [`0002_calendar_days.sql`](migrations/0002_calendar_days.sql)は予定・来館フラグを独立保存する。[`0004_calendar_rest_days.sql`](migrations/0004_calendar_rest_days.sql)は明示的休息日フラグを追加し、既存行をすべて休息未指定（0）のまま保全する。**[`0003_exercise_catalog.sql`](migrations/0003_exercise_catalog.sql)** は種目名を主キーとした種目設定（部位・単位）の保存と、記録時の`entry_unit`・`duration_seconds`追加用。既存の重量・回数の記録はデフォルト`kg_reps`として保つ。既存のトレーニング記録は自動で来館扱いに変換しない。**[0005_weekly_plans.sql](migrations/0005_weekly_plans.sql)** では毎週の曜日ルールと日別例外用に2テーブルを追加し、既存の休息日・来館・筋トレ実績は移行／削除しない。SQLファイルの存在は本番適用の証拠ではなく、`/api/health`の`SELECT 1`成功もテーブル・保存処理の証明ではない。

既存DBを削除・再初期化しない。初回セットアップ時はD1 Consoleまたはマイグレーションで適用するが、過去のConsole適用とマイグレーション管理の差を先に確認する。既存の列構造とデータを確認し、必要な追加マイグレーションを用意する。

### ジム16機種の初期登録（0006）

`migrations/0006_gym_machine_catalog.sql` は、ユーザー指定の筋トレマシン16種類を既存の `exercise_catalog` に追加入力する。5機種は0003に登録済みであり、`INSERT OR IGNORE` で既存の個別設定を保持し、他の11機種を追加する。部位は主要な対象部位1種類、単位はすべて `kg_reps`（kg＋回数）。ユーザー指定の「ヴァーディカルトラクション」「POTARYTORSO」は、それぞれ「ヴァーティカルトラクション」「ロータリートーソ」の表示名で登録する。元の11標準種目や既存の記録・予定を削除しない。

既存本番DBでは0006の適用後に `GET /api/exercises` の `catalog` へ反映される。main更新やWorkers BuildsのみではD1マイグレーションは実行されない。0003適用状態・本番マイグレーション履歴とテーブルの存在を確認してから、0006を安全に適用する。未適用時は初期候補に新機種を表示しても、D1登録済みとは見なさない。

### 入力内容ごと繰り返す（0007）

- 新規 `migrations/0007_repeat_workout_snapshot.sql` が `workout_repeat_series`／`workout_repeat_exceptions` を追加。種目・単位・全セットの重量／回数／秒・種目別メモ・順序を一つのJSONスナップショットとしてD1へ保存する。**workout_sessions／workout_setsへ未来の実績を挿入しない**。
- 日・週・隔週・月単位で開始日・任意の終了日を指定し、カレンダーにはその日の予定として合成する。月末が存在しない場合（月次31日→11月など）はその月をスキップする。休息日と手動の日付例外は予定表示より優先する。
- 該当日の記録画面へスナップショットを未実施の下書きとして展開。実績がある同名種目は既存の保存内容を優先し、記録を上書きしない。入力から繰り返し設定する際に実績の保存は必須としない。実際の筋トレ実績は既存の種目別保存ボタンでのみ確定。
- 編集・削除範囲は「この予定のみ」「この予定以降」「すべての予定」。個別差分を別テーブルへ保存し、以降の変更は期間分割する。周期・終了日はシリーズの編集範囲に合わせて変更可能。
- 以前の0005「曜日だけ繰り返す」予定は削除・自動移行しない。旧APIは互換性のため残すが、新規登録UIは内容の複製方式へ置き換えた。旧曜日ルールに種目内容は無い。
- **本番で有効化するには0007のD1マイグレーションが別途必要**。既存適用履歴・0004/0005/0006の状態を先に照合し、既存データを削除・初期化しない。未適用時は繰り返し編集を無効化し、通常の実績記録・旧予定・休息日を維持する。

## API（個人用）

| HTTP | エンドポイント | 内容 |
|---|---|---|
| GET | `/api/health` | 公開診断。D1接続とSecret設定有無 |
| POST | `/api/login` | パスワード認証、Cookie発行 |
| GET | `/api/session` | Cookie検証。未認証は401 |
| POST | `/api/logout` | Cookie破棄。認証前にも扱う |
| GET | `/api/workouts?month=YYYY-MM` | 月別記録・セット明細、最大200件（上限時は`truncated`） |
| POST | `/api/workouts` | 日付・メモと任意の`sets`を新規保存（旧形式も許容） |
| PUT | `/api/workouts/:id` | 日付・メモ・全セットをトランザクションで更新 |
| DELETE | `/api/workouts/:id` | 記録とセット明細を削除 |
| GET | `/api/exercises` | D1の種目設定（種目名・部位・単位）と実施済み種目を返す。0003未適用の場合は`catalog_ready:false`で従来の記録名だけ返し、既存の記録を継続可能 |
| PUT | `/api/exercises/catalog` | 種目名・部位・単位を登録・編集。名前変更時は過去のセット名も一括更新して履歴の一致を維持。同名への衝突は409、0003未適用は503 |
| PUT | `/api/exercises/log` | 日付＋種目名＋その種目のセットとメモを独立保存。日付・種目名が一致する単一種目記録は更新 |
| DELETE | `/api/exercises/log` | JSON `{performed_on, exercise_name}`の指定日・指定種目のセットを削除。複数種目セッションは他種目を保持、空セッションのみ削除。認証・同一Origin・JSON必須 |
| GET | `/api/exercises/history?name=種目名` | 種目別セット履歴（最大1200セット、`truncated`で表示上限通知、認証必須）。分析の実施日一覧から共通の編集画面へ接続 |
| GET | `/api/workouts/recent?name=種目名&before=YYYY-MM-DD` | 同名種目の前回セット（最大12セット＋`truncated`）。`before`指定時はその日より前の最新実績、未指定時は従来どおり最新実績 |
| GET | `/api/calendar?month=YYYY-MM` | 単発＋毎週＋日別例外の有効予定・来館・休息。未適用の場合は`rest_ready:false`（0004）／`recurrence_ready:false`（0005）で各機能のみフォールバック |
| PUT | `/api/calendar/YYYY-MM-DD` | 指定日の予定・来館と任意の休息日`rest`。0005適用後は予定ON/OFFを日別例外で上書きし、休息日・従来単発・実績を保持。0005未適用でも0004までの動作を維持 |
| PUT | `/api/calendar/recurrence` | `{start_on,weekdays:[1..7]}`で複数曜日を毎週設定。選択日より前のルールは保存し、以後を編集。空配列は以後終了。0005未適用は503 |
| POST | `/api/calendar/move` | `{from_date,to_date}`の今回だけ日付変更。移動元を例外OFF／移動先を例外ONへ一括保存。移動先に予定・休息があれば409。来館・実績は変更しない |
| GET | `/api/repeat?date=YYYY-MM-DD` | その日に適用される実績とは独立した種目スナップショットと繰り返し情報。0007未適用は`ready:false` |
| POST | `/api/repeat` | 現在の全種目・全セット・メモ・周期・終了日を繰り返し予定として保存。実績は作成しない。0007未適用は503 |
| PATCH | `/api/repeat/:id` | `date`と`scope: only/future/all`に応じ入力内容・繰り返し周期・終了日を更新 |
| DELETE | `/api/repeat/:id` | `date`と編集範囲に応じて当該回のみ・今後・全体を削除。既存実績は残す |

日付は2000～2100年の実在日、メモは最大300（JavaScriptの`length`）。同日複数記録が可能。実施日数と件数は別で、月200件超は全件集計にならない。種目は60文字以内、1件最大48セット。セットごとに重量（0〜2000kg）・回数（0〜1000回）を保存する。新しい種目別保存ではNFKC正規化・空白除去・英字小文字化した種目名を共通キーとして扱い、専用の種目IDは設けない。各種目1～12セットを日付ごとに保存し、他種目の記録は変更しない。旧式の全種目一括保存APIは互換性維持のため残す。休息日は0004適用後に日付別`rest`フラグへ手動保存。予定と休息は排他的で、来館・実績は独立。未記録日を自動的に休息日にしない。毎週繰り返し予定・今回だけ休み／日付変更・選択日以降の編集は0005適用後に使用可能（休息日が優先）。種目テンプレート・お気に入りの永続保存・設定保存APIは未実装。単発の予定・来館はスイッチ切り替え時にD1へ保存する。Secret未設定・不正長では`/api/health`以外のAPIは503。

### 旧・曜日だけの毎週予定（0005・API互換用）

- 旧APIにおける曜日単位の予定保存は残す。現行の記録画面は0007の入力スナップショット繰り返しUIに置き換えており、0005の曜日設定ボタンは表示しない。
- 「今回だけ休む」は日別例外をOFF、「この日だけ移動」は元日OFF／移動先ONで保存。毎週ルールや来館、実施内容は変更しない。移動先が休息日や予定ありなら409で中止。休息日は予定より優先し、カレンダーの休息日表示も維持する。
- 予定と休息日は同日で両立させない。休息日指定を取り消しても、個別に休みにした例外はそのまま残る。週次ルール再設定後も過去の例外は維持。
- 本番D1は**0004の休息列の状況確認後、0005の追加テーブルを安全に適用**する。Cloudflare Workers Builds／main更新ではマイグレーションは自動適用されない。0005未適用でも既存の休息日・来館・単発予定は利用できる。本番D1を初期化しない。
- 繰り返しの停止は選択日以降から。通知、曜日別種目テンプレート、予定の開始・終了時刻は未実装。

## 表示の開発設定

ホーム右上の「開発」で、ホームに重ねる小型パネルを開閉する。衣装（トレーニング／部屋着）、場所（ジム／街／大学／栞の部屋）、背景の時間帯（自動／朝／昼／夜）を変更すると、その場で反映する。私服は立ち絵準備中。パネルを開いたまま連続して切り替えられ、画面遷移・暗転はしない。

変更はメモリのみで保持し、再読み込み・再ログインでリセットする。「リセット」はトレーニング衣装・時間帯自動・場所再抽選へ戻す。時間帯固定は背景だけに適用し、セリフや記録日時を変更しない。×・開発ボタン・Escapeで閉じる。他画面やメニューを開く場合、ログアウト時にも閉じる。


## ギャラリー（画像差分の比較）

メニューの「ギャラリー」で、登録済みのジム・第1話の5表情（通常／考える／驚き／笑顔／いたずら）、部屋着7表情、ジム用SDを閲覧できる。第1話の5表情は「切替」で修正前・修正後を同じ表示枠で入れ替え、「横並び」で同時比較する。狭幅端末では左右にスクロールする。

画像パスの管理は `public/data/shiori-gallery.json`、表示処理は `public/gallery.js`、スタイルは `public/gallery.css`。登録済みのWebPを参照するだけで、画像の再保存・加工・自動補正・採用判定はしない。ギャラリーの選択はメモリ内のみ、イベント再生やD1の記録へ影響しない。表示時に初めて素材一覧を読み込む。Android実機でのUI確認と本番の公開確認は別工程。

## 栞の表示素材

人物素材は`public/assets/shiori/{home|gim|town|College}/{v1|v2|…}/`で場所→衣装別に管理する。`v1`・`v2`は衣装IDであり、画像の改訂番号とは分ける。配置・命名・制作プロンプトは[visual.md第6節](docs/shiori/visual.md)を参照。現行ホームの衣装選択は`gim/v1`のトレーニング画像と`home/v1`の部屋着テスト画像を参照する。場所と衣装は開発パネルで独立して切り替え、背景との自動連動は未実装。

### カレンダー・記録・分析のSD固定レイアウト

カレンダー・記録・分析の3画面は、固定ヘッダーより下の画面領域を共通で「**上部の個別スクロールコンテンツ**／**下部の固定高さSD栞＋吹き出し**」へ分割する。SD表示領域は3画面で同じCSS変数 `--sd-fixed-height`（通常 `clamp(132px, 19dvh, 182px)`）を使い、スクロール、データ件数、種目編集・履歴表示などで高さや下端位置が変わらない。低い画面／狭幅では3画面一律に省スペース値へ切り替える。スクロールするのは上段だけで、SD領域をページ全体の末尾に押し出さない。

既存のカレンダー・記録のSD画像、吹き出しとタップによるセリフ再抽選を維持。分析画面にも同じ登録済みSDテスト素材と吹き出しを置き、既存のホーム用採用済みセリフ候補を利用する。認証前・他画面・ホームの画面構成は変更しない。Androidではキーボード表示によりスクロール可能な上段が縮むが、SD領域の確保とスクロール分離は保つ。

### 分析から記録までの共通動線

- **分析**：実施済み種目一覧 → 種目別の実施日一覧 → **共通の種目記録編集画面**。実施日の重量・回数・セットを確認し、そのまま編集・保存できる。分析経由で「戻る」または保存を行った場合は、その種目の実施日一覧へ戻る。
- **カレンダー・記録**：日付を選択 → その日の種目一覧 → 同じ種目記録編集画面。こちらから戻る、または保存した場合は日別の種目一覧へ戻る。
- 共通の記録編集画面では**各セットの重量・回数のそれぞれの入力欄の直上に前回値を表示**し、入力中に列ごとに比較できる。セット番号を左の小列にまとめ、入力欄44pxを維持したコンパクトな4列配置として、標準的なAndroid縦表示で3セット程度をスクロールせず確認できる密度を目標にする。セット入力欄は最初の3セットの実測高さを最大高とし、1〜3セットなら内部スクロールなし、4〜12セットでは**セット欄内だけ縦スクロール**する。4セット目の追加時は入力欄へ自動スクロールする。端末の文字サイズ・幅が変わった場合にも高さを再計算し、ソフトウェアキーボード表示中などは従来の画面スクロールも利用できる。**保存は編集画面右上のフロッピーディスク形アイコン**（44px、アクセシブルな名前「この種目を保存」）から行う。新規または重量・回数・セット・メモに未保存の変更がある種目には、種目カードの名前横と編集画面の保存アイコン右上に小さなドットを表示し、保存成功後は消す。「未保存」の可視テキストは設けないが、保存ボタンと種目カードの読み上げラベルでは未保存状態を案内する。対応する前回セットがない場合は「前回：—」とし、今回の値を自動変更しない。前回セットのコピーは別の明示操作。セット追加・削除、種目単位のD1保存を使い回す。分析には別の編集フォームを作らない。種目一覧・実施日一覧は認証付きAPIから取得する。
- 分析は現段階では実施種目／実施日への導線。重量推移グラフ等の集計は未実装。履歴APIには上限があるため、表示が一部の場合は案内する。

### 種目設定・部位フィルター・単位

- 種目の設定画面はメニュー／記録画面／種目選択／分析画面から開ける。種目名（最大60文字、NFKC正規化・空白除去・英字小文字化で識別）、部位（胸・背中・肩・腕・脚・腹筋・全身・その他）、単位（**kg＋回数／回数のみ／秒**）を設定する。記録・分析の種目一覧には**部位フィルター**を用意し、検索と併用可能。
- IDマスターは作らず`exercise_catalog.exercise_name`を主キーとする。0003を適用すると既存の固定候補11種目を初期登録。D1に既にある実施済みの名称も統合表示し、編集すると設定として登録できる。履歴のある種目名を変更した場合は、古い表記を正規化して一致する`workout_sets.exercise_name`を同一トランザクションで更新する。変更先の種目名が既に存在すれば衝突エラー。過去の日時・数値・来館履歴は維持する。
- 記録画面は選択した単位に従って、kg＋回数の場合は重量と回数、回数のみは回数欄、秒は秒数欄を表示。秒は1～36000、回数は0～1000、重量は0～2000kg。秒は`duration_seconds`、回数・kg＋回数は従来の`reps`／`weight_kg`へ保存。セットには`entry_unit`を保持し、設定の単位変更後も**過去の記録の単位は書き換えない**。履歴・前回比較も記録時の単位で表示し、異なる単位の前回記録は数値のコピー対象にしない。
- **D1の0003適用が必要**：Cloudflare WorkersのソースがmainからビルドされてもDBマイグレーションは自動で適用されない。既存のD1 Console適用履歴・マイグレーション管理を確認してから、未適用部分を追加する。`npm run db:migrate:remote`は必要な実施を確認したうえで行い、既存データや0001/0002を再初期化しない。未適用時は種目設定の保存が無効になり案内を表示する。既存のkg＋回数の記録APIと一覧取得は従来どおり利用できる。

### 記録画面の操作

共通種目エディタは、画面上部を「戻る矢印・種目名・保存アイコン＋未保存ドット・ゴミ箱アイコン」の**1行**に集約する。その直下は実施日と前回実施日（または取得状態）を横並びの細い1行として表示し、以前の大きな戻るリンク・種目名・日付・前回日の縦4段を廃止する。戻る矢印は44px級の操作領域を維持し、入口に応じた「その日の種目一覧へ戻る／実施日一覧へ戻る」をアクセシブルな名前・ツールチップに設定する。これまでセット入力上部にあった前回実施日メッセージはヘッダーへ移し、同一要素で取得中／成功／失敗を更新する。セット数・記録値・前回コピー・保存処理・3セットまで非スクロールは変更しない。


数字入力を簡単にするため、各セットの「前回：○kg／○回」を押すと該当する重量または回数だけ今回の入力欄に転記できる。重量と回数の入力欄はそれぞれ**一体型の入力ボックス内に「−｜数値（kg／回）｜＋」を配置**する。3か所の独立した枠は使わず、左右操作と中央入力の間にも区切り線を置かず、外側の角丸枠だけでひとまとまりにして視覚的な圧迫感を抑える。重量・回数の独立した見出しは各セットから省き、中央の数値だけを直接編集する。数値型inputには文字列の単位を混ぜず、視覚表示だけを重ねる。スクリーンリーダー向けには各セット番号付きの重量・回数ラベルを維持する。重量は±2.5kg、回数は±1回の操作ができ、中央の数値をタップするとキーボードで直接入力できる。別置きの数値調整バーは使わない。Enterは次の入力欄へ進む（意図しない保存を防止）。前回値コピー・増減は未保存ドットに反映する。**保存ボタンでD1に記録を確定しても編集画面に留まり、保存結果を表示する。**分析・記録のどちらの入口でも、戻るボタンを使うまで移動しない。保存した後に続けて修正し、再保存できる。

種目選択画面の候補一覧は**単独のスクロール領域を作らず**、記録画面共通の上段スクロール領域（`#record-scroll`）に含める。候補が画面内に収まらない場合は上段コンテンツ全体をスワイプして一覧の続きを見る。下部SD栞と吹き出しは固定したまま。候補画面を開いた瞬間の入力欄への自動フォーカスは行わず、戻るボタンを`preventScroll`付きでフォーカスして上段を先頭へ戻す。検索したい場合のみユーザーが入力欄をタップする。

記録画面は日付・予定・来館と、その日の種目カード一覧を表示する。「種目を追加」で固定候補および過去に登録された種目を検索・選択して種目専用編集ビューへ進む。種目名は履歴整合のため選択時に正規化して固定する。前回の重量・回数を見ながらセットを入力し、**「この種目を保存」**で選択中の種目だけCloudflare D1へ保存し、**編集画面を開いたまま**保存結果を表示する。異なる種目はまとめて保存しない。既存の同日種目カードは直接開いて更新できる。

編集画面右上のゴミ箱アイコンは確認ダイアログを出し、未保存の新規種目なら画面内の入力のみを破棄する。保存済みならその日・その種目の全セットをD1から削除する（他の日付・種目・来館予定は維持）。保存済み記録の削除に失敗した場合は入力を消さずエラーを表示する。削除成功時は入口に応じて日別種目一覧／分析の実施日一覧へ戻る。種目マスター自体を一括削除する操作ではない。
 
種目を選択しただけでは記録は保存されない。編集中の値はページ内移動中はメモリで保持するが、再読み込み・ログアウトで破棄する。未保存の入力がある場合、日付変更時に確認する。過去の履歴と種目別集計はそれぞれ別の画面／APIで確認できる基盤を維持する。

### カレンダー・詳細記録の導入とDBの注意

- 追加機能は、来館・予定と筋トレ内容を独立管理する。来館登録だけなら種目入力は不要で、過去のメモのみの記録も残る。月の記録上限200件は継続。前回記録の参照は種目名の完全一致で取得する。
- `0002_calendar_days.sql` は**追加テーブルのみ**。既存の `workout_sessions` と `workout_sets` に対する破壊的変更はしない。
- **GitHubへのコミットやWorkersへのデプロイだけでは本番D1にマイグレーションが適用されない**。D1 Consoleで現行テーブルとマイグレーション適用履歴を確認し、既存のConsole適用と食い違わないことを検査してから0002を本番へ適用する。
- 0002未適用時は予定・来館欄に準備が必要と表示し、既存のトレーニング記録の読み出しと入力は継続する。本番DBの適用と実機検証は別途必要。
- 編集中のフォームは画面間移動では維持されるが、再読み込み・ログアウトで破棄される。個人データをブラウザの永続ストレージへ保存しない。
