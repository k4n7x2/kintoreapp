# 3プロジェクトの共通案内・導入手順

## 1. 作業先と指示

それぞれの**専用指示ファイルの全文**を、対応するChatGPTプロジェクトの指示欄へ貼る。この共通案内は資料として参照する。全プロジェクトで同じリポジトリの`main`を正本とし、別プロジェクトの会話や添付が自動共有される前提にはしない。

| プロジェクト名 | 担当 | 貼り付ける専用指示 |
|---|---|---|
| kintoreapp｜アプリ開発 | 筋トレ管理・UI・認証・保存・素材の組み込み・公開・全体企画 | [development-handoff.md](development-handoff.md) |
| 朝倉栞｜ビジュアル制作 | 立ち絵・衣装・表情差分・背景・画像検査 | [visual-production-instructions.md](visual-production-instructions.md) |
| 朝倉栞｜セリフ・物語制作 | ホームの一言・会話・日常エピソード・季節イベント・文章検査 | [dialogue-production-instructions.md](dialogue-production-instructions.md) |

全体の目的は「簡単な筋トレ記録と栞との日常によって、また開きたくなること」。Android縦画面、データ保全、原則無料、人物の一貫性、休んだ日を責めない体験を共通の判断基準にする。

## 3. 制作物の状態と受け渡し

| 段階 | 記録する根拠 |
|---|---|
| 構想・候補 | アイデアや試作。採用・表示・正史化の根拠にはしない |
| 採用済み | ユーザーが採用した対象・版・範囲。設定の採用と作品の採用は区別 |
| GitHub登録済み | ファイル実体とコミットSHA。登録だけでアプリ実装済みとしない |
| 実装済み | 読み込み・条件判定・表示／保存のコードへの接続 |
| 公開済み／本番確認済み | ビルド・デプロイの証拠と、実際の応答・表示の証拠を別々に記録 |

制作側からアプリ開発へ渡す際は、次の欄を成果物に添える。小さな追加ならチャットの受け渡し文でよく、別の管理台帳を毎回作らない。採用登録が済んでいればコミットURLから辿れるようにする。

```text
【制作物の受け渡し】
対象・版：
参照したmainのSHA／資料・画像の版：
現在の段階・採用指示の範囲：
用途・対象画面：
表示条件／表示してはいけない条件：
設定への影響：なし／変更候補／採用済み変更と正本の更新先
ファイル：実ファイル・パス・形式（画像は寸法と透過、本文は件数と構造）
組み合わせ：必要な衣装・表情・背景・本文（指定なしならその旨）
検査済み事項／未確認事項：
次の工程：素材登録／既存データへの追加／条件機能の実装等
```

- **画像**：人物立ち絵は原則実アルファ付きPNG。採用済みWebP例外や背景の形式は`visual.md`・既存素材を参照する。制作原本と表示最適化版を区別し、変換を無断で一般化しない。
- **セリフ**：既存ホーム用データへ追加するなら、その時点の文字列配列構造を維持したUTF-8 JSONを渡す。新規イベント・長編はMarkdownの台本と前提・順序・再表示条件を渡し、対応機能をアプリ側で設計する。必要条件が未実装の台詞は無条件候補へ追加しない。
- **設定・出来事**：本文を書いたこと、採用したこと、栞の正式な過去やユーザーとの約束にしたことは別。人物設定の採用は`character.md`へ、採用された継続エピソードを別資料に置く場合は`shiori/README.md`から案内する。現時点で独立した正史・年表ファイルはない。
- **並行作業**：共通文書を変更する前とコミット直前にmainを再確認する。同じ資料の同時編集は合流してから反映し、他の成果物や試作を上書きしない。採用・反映済みの指示は繰り返し確認しない。

## 4. 各プロジェクトへ登録する資料

文書は最新mainから取得した参照用の写し。作業時にはGitHubの更新を確認する。コード全体や全画像を3か所へ常時複写する必要はない。GitHubに接続できない作業では、必要な関連ファイルを同じSHAで追加する。

| 登録先 | 初期登録する文書 | 初期登録する画像 | 作業に応じて追加 |
|---|---|---|---|
| アプリ開発 | 本書、ルート`README.md`、`docs/implementation-status.md` | 必須なし | 変更対象のコード・設定、画面スクリーンショット、採用素材。キャラ演出変更時は`shiori/README.md`が指定する資料 |
| ビジュアル制作 | 本書、`docs/shiori/README.md`、`character.md`、`visual.md`、`dialogue.md`、`character-sheet-spec.md`、`reference-audit.md`（後ろ5件も`docs/shiori/`配下） | 下表の正式画像6枚。添付PNG3枚は差分参考として分けて登録可 | 表示中の衣装・表情素材、対象シーンの背景と`backgrounds-manifest.json`、レイアウト確認用スクリーンショット |
| セリフ・物語制作 | 本書、`docs/shiori/README.md`、`character.md`、`dialogue.md`、`docs/implementation-status.md`、`public/data/shiori-greetings.json` | 必須なし | 外見・表情を扱うときの`visual.md`と画像、`shiori-login-dialogues.json`等の未接続候補、採用エピソード |

### ビジュアル制作の画像一覧

正式画像はすべて`docs/shiori/reference/`にある。**GitHubからダウンロードした実ファイルをプロジェクトのソースへアップロードする**。URLだけの登録では画像ツールへの入力が確認できたことにならない。

| 役割 | 正式画像として登録するファイル | 今回の添付との関係 |
|---|---|---|
| 顔・瞳・表情 | `shiori-master-v1.jpg` | 添付`shiori-master-v1.png`は描画差のある参考版 |
| 塗り・光・透明感 | `shiori-style-fullbody-v1.jpg` | 添付`shiori-style-fullbody-v1.png`は描画差のある参考版 |
| 体型・三面図・私服 | `shiori-character-sheet-v1.jpg` | 添付`shiori-character-sheet-v1.png`は描画差のある参考版 |
| 衣装A | `shiori-training-outfit-v1.jpg` | 今回の添付とバイト一致。その添付を利用可 |
| 衣装B | `shiori-training-outfit-v2.jpg` | 今回の添付とバイト一致。その添付を利用可 |

PNG3枚を追加する場合は「差分参考・正式採用未確認」と明示する。正式JPEGと無断で置換しない。個別制作でPNGを使う指定と、正本を新版へ更新する採用判断は別。詳細とファイル識別用ハッシュは`reference-audit.md`に集約する。

登録名が衝突する場合だけ、参照コピーに次の名前を使う。リポジトリの実ファイル名は変更しない。

| 元のパス | アップロード時の名前 |
|---|---|
| `README.md` | `kintoreapp-README.md` |
| `docs/shiori/README.md` | `shiori-README.md` |

初回登録時にプロジェクト内のチャットへ「資料コピーの取得元main SHA：…、登録日：…、上表以外の改名：…」を残す。以降、正式資料の更新時に該当コピーを置き換える。古い指示を追加で積み重ねない。

## 5. ChatGPT上で行う操作

1. ChatGPTのプロジェクト一覧から、上表の3つの名前でプロジェクトを作成する。既存「筋トレアプリ開発」をアプリ開発用に使う場合は、そのプロジェクトの指示を新しい専用指示へ置き換えてよい。
2. 各プロジェクトの指示欄へ、対応する専用指示の全文だけを貼り付けて保存する。旧来の全分野を含む長い指示は併記しない。
3. 各プロジェクトのソース／ファイル追加から、前節の資料・画像を登録する。GitHubプラグインで`k4n7x2/kintoreapp`を参照できる状態を用意する。画面の項目名は利用環境で異なるため、指示欄とソース欄を区別する。
4. 各プロジェクトで新しいチャットを開き、「GitHub最新mainのSHAと担当資料を確認し、このプロジェクトの担当範囲と不足資料を短く報告してください。変更はまだ行わないでください」と送る。ビジュアル側には画像の読み取り・目視確認も依頼する。画像ツールへの入力テストには別途、画像制作の依頼が必要。
5. 以後は成果物ごとにチャットを分け、採用物を前節の受け渡し欄で次の担当へ渡す。過去チャットを一括移動する必要はない。既存のホーム配置調整はアプリ開発側で続ける。

プロジェクト作成、指示の設定、ソース登録はこの文書をコミットしても自動実行されない。公式の一般案内：[Projects and chats](https://learn.chatgpt.com/docs/projects)（2026-10-15参照）。
